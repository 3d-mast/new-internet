# Протокол LICHEN/2

## 1. Идентичность

Каждый узел создаёт локальную пару Ed25519. `node_id` — Base32 без padding от первых 16 байт SHA-256 публичного ключа. Приватный ключ не покидает устройство, кроме явно созданной пользователем зашифрованной резервной копии.

## 2. Транспорт

Текущая версия использует TCP и TLS 1.3. Сертификаты самоподписанные, но доверие не строится на сертификате или публичном CA: сторона сравнивает Ed25519-ключ сертификата с ключом, закреплённым в приглашении или локальном хранилище доверия.

После TLS передаётся length-prefixed JSON frame:

```text
uint32_be length
JSON payload
```

Максимальный размер управляющего frame — 1 MiB.

## 3. Hello

`Hello` содержит версию, ID, имя, публичный ключ, назначение соединения, timestamp и Ed25519-подпись всего объекта без поля `signature`.

Назначения:

- `join` — принять одноразовое приглашение;
- `control` — проверка доступности;
- `exit` — TCP-поток к интернет-адресу;
- `tunnel` — TCP-поток к сервису локальной сети;
- `relay` — открыть непрозрачный канал к другому узлу;
- `backhaul` — зарегистрировать обратный исходящий канал для узла за NAT.

Timestamp принимается только в окне ±2 минуты.

## 4. Приглашения

Формат:

```text
lch1.base64url(JSON)
```

Payload подписан приглашающим узлом и содержит:

- идентичность;
- endpoints;
- одноразовый случайный код;
- срок действия;
- точные разрешения.

Код помечается использованным атомарно при успешном `join`.

## 5. Направленные права

У каждого peer хранятся два независимых набора:

- `permissions` — что локальный пользователь разрешил удалённому узлу;
- `capabilities` — что удалённый узел разрешил локальному.

Это устраняет двусмысленность первой версии протокола.

## 6. Relay с end-to-end шифрованием

### Прямой relay

1. Origin устанавливает внешний TLS с relay.
2. Relay открывает обычное TCP-соединение до TLS-listener destination.
3. Origin создаёт **вторую TLS-сессию** поверх внешнего канала с pinning ключа destination.
4. Relay проксирует зашифрованные байты и не имеет ключа внутренней сессии.

### Обратный backhaul через NAT

1. Destination сам устанавливает исходящий TLS к relay с purpose `backhaul`.
2. Relay хранит канал ограниченное время.
3. Origin запрашивает destination через relay.
4. Relay связывает origin с ожидающим backhaul.
5. Origin и destination создают внутренний TLS поверх двух внешних каналов.
6. После завершения destination автоматически регистрирует новый backhaul.

Это позволяет destination находиться за NAT при условии, что он и origin имеют исходящий доступ к одному доверенному relay.

## 7. Exit и LAN

- `exit` требует одновременно `OfferExit=true` на сервере и `permissions.use_exit=true` для вызывающего узла.
- Приватные, loopback и link-local адреса дополнительно требуют `permissions.access_lan=true`.
- `tunnel` всегда требует `permissions.access_lan=true`.

## 8. Локальные прокси

- SOCKS5 поддерживает CONNECT для IPv4, IPv6 и доменных имён.
- HTTP proxy поддерживает CONNECT и обычные HTTP-запросы.
- Оба прокси передают TCP-поток через выбранный exit node и могут использовать relay/backhaul.

## 9. Известные ограничения

LICHEN/2 пока не является IP-протоколом полного туннелирования: нет TUN, UDP, QUIC и мультиплексирования. Вложенный TLS защищает содержимое от relay, но не скрывает метаданные соединения.
